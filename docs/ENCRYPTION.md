# Encryption in Muni

Status: implemented for **new sprints** (`sprints.encryption = 'e1'`), tested (below), **not
independently reviewed**. Not deployed by this change. Legacy sprints are unchanged and labelled.

## 1. The protection, precisely

**Goal.** Someone inspecting Muni's Cloudflare D1 database, Durable Object storage, backups or
routine logs cannot read the retrospective content of an encrypted sprint. The backend never
possesses a key that opens it: content is encrypted in an authorized participant's browser before
upload and decrypted only in authorized browsers.

**Trust assumptions.**

- The frontend delivered from act.munimuni.app is genuine. Whoever controls that code (operator,
  compromised deploy pipeline, compromised Cloudflare account) can capture plaintext or keys,
  substitute public keys, or add recipients. This design does **not** resist an actively
  malicious operator; it removes the *stored* and *routine* ability to read content.
- The backend stores and forwards public keys, wrapped keys and envelopes honestly for
  availability; if it doesn't, the failure mode is denial of service or a detectable substitution,
  not plaintext disclosure (except via the frontend, above).
- Participant devices are not compromised. No protection against malicious extensions,
  screenshots, or authorized participants sharing what they read.

**Out of scope.** Email addresses and account metadata (sign-in is unchanged: email codes).
Authorship: the server still records which account submitted each record — encryption hides what
was written, not who wrote it.

## 2. Content inventory

| Content | Where it lived | Encrypted sprint |
| --- | --- | --- |
| Thought text, impact, what might help | `entries.body/impact/might_help` | One entry envelope in `body`; `impact`/`might_help` NULL |
| Edited thoughts | same rows (overwritten) | New envelope, fresh content key |
| Drafts, unsent thoughts | browser only (never uploaded) | Plaintext in the browser; sealed at send time |
| Context added in the retro | `context_additions.body` | Field envelope |
| Theme title, summary, question, draft experiment, order reason | `themes.*` | Field envelopes |
| Discussion notes (takeaway, what happened, impact, could try, notes) | `discussion_notes.*`, returned in stage snapshots | Field envelopes |
| Experiment change, success signal, outcome note; copied theme title | `experiments.*` | Field envelopes (copy is the theme's envelope) |
| Recap | `recaps.body` | Field envelope; the server-side draft generator is refused |
| Opening question | `sprints.opening_question` | Field envelope |
| Vote-reset reason typed by the facilitator | `vote_rounds.cancel_reason` | Field envelope (system reasons stay plain) |
| Agenda reasons | Durable Object `meeting.agenda[].reason` | Opaque envelope (from themes) |
| AI grouping input/proposals | `ai_jobs`, `ai_proposals`, provider | **Disabled**: refused server-side, `ai_processing` forced off |
| Exports (.md, .csv, raw) | generated by the Worker | **Refused** server-side; built in the browser from decrypted data |
| Live socket messages | hints only (`{type, resource, version}`) | No content (unchanged) |
| Logs | `console.error` on failures: path, method, error text | No content (error messages never include field values) |

**Deliberately visible metadata:** workspace/sprint names, sprint goal, external id, dates, retro
time and timezone, participants and facilitator, category and period per thought, authorship and
timestamps (server-side only; shared views still never show them), theme membership and counts,
vote rounds and totals, experiment owner/review date/status, audit events, email addresses, key
fingerprints, which key versions each person holds. The setup screen tells facilitators the name
and goal are not encrypted.

## 3. Collection and reveal: options

| Option | Crypto sealing vs teammates | Offline authors at reveal | Recovery | Early read by facilitator | Operator can read |
| --- | --- | --- | --- | --- | --- |
| A. One sprint key for all participants from the start | No (server-enforced only) | Fine | Simple | Yes, if served ciphertext | No |
| B. Per-author keys released by authors at reveal | Yes | **Blocked** until each author is online | Per author | No | No |
| C. Threshold / time-lock escrow | Yes | Fine | Complex | No | Needs a trusted third party (rejected: escrow) |
| **D. Sprint key pair; secret held only by the facilitator until close (chosen)** | Yes vs non-facilitators; server-enforced vs facilitator | Fine | Facilitator's devices must hold it at close | Only if the server hands them ciphertext early | No |

**Decision (D).** Each thought is encrypted with a fresh content key, sealed twice: to the
sprint's public key and to the author's own account key. While collecting, the sprint secret is
sealed only to the facilitator (the server refuses wraps to anyone else for a still-sealed
version). Closing collection *is* the reveal: the facilitator's browser seals the secret to every
participant, stored atomically with the status change.

What this preserves: other participants cannot decrypt anyone's thoughts before reveal, even with
the ciphertext; authors read and edit their own thoughts at any time; authors don't need to be
online at reveal; the operator holds no key.

What it concedes, explicitly: the facilitator's devices hold a key that could open thoughts
early. Muni's server doesn't give them the ciphertext before close (the existing, tested rule),
but that is **server enforcement, not cryptography** — a facilitator colluding with the operator
could read early. If the facilitator loses every device and their recovery key *before* closing,
the sprint cannot be revealed: authors can still read their own thoughts, and the team needs a new
sprint. We accept that availability cost rather than add escrow.

**Reopen:** a new key version is created on the facilitator's device and sealed only to them;
thoughts written after reopening use it, and closing again reveals it. What was revealed before
stays readable (as before). **Late participants** receive every revealed version from any
teammate's device that holds it. **Facilitator change** moves the key: the old facilitator's device
seals it to the new one in the same request; the server then drops other wraps of the sealed
version. **Rescheduling** has no key effect.

## 4. Keys: authentication and encryption are separate

- **Account key.** X25519, generated in the browser on first setup. The public key is published
  (`account_keys`); the private key stays in IndexedDB (`muni-keys`). Nothing is derived from the
  email address or sign-in codes.
- **Recovery key.** 160 random bits + 16-bit checksum, shown once as nine groups of four
  (Crockford base32). The server stores the private key sealed under HKDF(recovery key) — it
  cannot open it. "Show a new recovery key" rewraps and invalidates the old one. People confirm
  they saved it; sign-out warns if they haven't.
- **Another device.** Sign in by email (account access), then unlock with the recovery key
  (content access). The unwrapped key must match the published public key.
- **All keys lost.** "Start over" publishes a new key (server bumps `key_version`, audits
  `keys.replaced`). Content sealed only to the old key (their own unrevealed thoughts) is gone;
  teammates can reshare revealed sprints after confirming the new key.
- **Account recovery ≠ content recovery.** Email sign-in never unlocks content (tested).
- **Revocation.** Removing a member or participant stops the server serving them anything new, and
  devices only share keys with current participants. Nothing can erase keys or content already
  received. Signing out deletes the device's key; "Remove the key from this device" too.
- **Substitution and added recipients.** Devices pin each teammate's public key on first use
  (TOFU). A later change is never used: sharing to that person stops and the facilitator sees
  "X's encryption key changed" with the new fingerprint until they confirm. The server also only
  accepts wraps for current participants, to their current key. **Not prevented:** a malicious
  server showing a fake key on first sight, or adding a fake participant whom devices then share
  with — both visible to people (participant list, fingerprints) but not blocked.

## 5. Formats and primitives

Audited `@noble/curves` (X25519), `@noble/ciphers` (XChaCha20-Poly1305), `@noble/hashes`
(HKDF-SHA256, SHA-256). All code in `web/src/lib/e2ee/crypto.ts` (~300 lines).

- **Sealed box:** ephemeral X25519 → HKDF(shared, salt = eph‖recipient, "muni sealed box v1") →
  XChaCha20-Poly1305, context string as AAD. Low-order keys refused.
- **Sprint secret S** (32 bytes) per version → HKDF → sprint X25519 key pair and discussion key.
  Wrapped per person as `w1.` bound to (sprint, version, recipient).
- **Envelopes** `e1.` + base64url(JSON), `v: 1`. Field: `{t:'f', s, k, f, n, c}` with AAD
  (sprint, version, field). Entry: `{t:'e', s, k, r, a, n, c, ws, wa}` with AAD (sprint, record,
  version, author); `ws`/`wa` seal the content key to sprint and author.
- **Nonces:** 192-bit random (XChaCha), fresh per encryption; fresh content key per thought/edit.
- **Binding and tampering:** AEAD failure, wrong sprint, wrong field, wrong record id → the value
  is shown as "Can't be shown on this device" — never ciphertext, never plaintext fallback. Record
  ids for thoughts and sprint ids for new sprints are client-chosen UUIDs so they can be bound
  before upload. *Limitation:* derived fields are bound to sprint + field, not record id, so the
  server could swap two themes' titles within one sprint (integrity only).
- **Server enforcement:** for `e1` sprints every content field must be a well-formed envelope
  (`worker/src/lib/sealed.ts`); plaintext is refused (`encryption_required`). Client revision 3
  is required so stale tabs can't write old payloads.
- **Concurrency/retries:** thought submission is idempotent on the client-chosen id (existing
  outbox). Sealing happens at send time; with no key, the thought stays queued as "waiting for
  this device's key". The service worker, which holds no keys, skips encrypted items.

## 6. Tests

- `web/src/lib/e2ee/crypto.test.ts` (15): round trips, wrong recipient/context, tamper, cross
  sprint/record/field substitution, relabelling, low-order keys, nonce uniqueness, recovery typos
  and wrong account, malformed envelopes.
- `web/src/lib/e2ee/keyring.test.ts` (10): decrypt at the API boundary, explicit locked marker,
  refusal to send plaintext without keys, TOFU key-change detection, sealed-version sharing.
- `worker/test/encryption.test.ts` (6): envelopes only, plaintext refused, sealing policy through
  reveal, reopen versioning, late participants, recovery vs email sign-in, key replacement, legacy
  untouched, AI/export/recap refused, **every D1 table and the room's storage scanned for the
  synthetic text, private keys and sprint secrets**.
- `web/e2e/encryption.mjs` (17): the real UI end to end, including request bodies captured in the
  browser, reveal, preparation, and a new device unlocked with the recovery key.

**What testing doesn't establish:** the correctness of the construction against a cryptographer's
review; side channels; behaviour under a malicious frontend; browser storage security; resistance
of the recovery flow to phishing; completeness of the inventory against future code. **Independent
cryptographic and application-security review is required before claiming more than this document.**

## 7. Migration and rollback

- **Schema:** `0003_encryption.sql` is additive (a column, three tables). Existing rows are not
  touched; every existing sprint has `encryption = NULL` and is labelled "Not encrypted".
- **First release boundary:** only newly created sprints are encrypted. No legacy content is
  migrated. A later client-side migration (facilitator's browser re-encrypts a completed legacy
  sprint, verifies each envelope decrypts, then overwrites) is possible but **does not remove
  plaintext from D1 backups (Time Travel, ~30 days) or files already exported**, and must not be
  presented as if it did.
- **Rollback:** do not roll the Worker back below this version while encrypted sprints exist: an
  older Worker would accept plaintext into them and older clients would render envelopes as text.
  If a rollback is unavoidable, first mark encrypted sprints read-only (a status guard), deploy,
  and communicate. Rolling back only the frontend is safe for data (the server refuses plaintext
  and the revision gate asks stale clients to reload).

## 9. Remaining risks

Malicious or compromised frontend; first-sight key substitution and fake recipients; metadata
(authorship, timing, categories, counts) visible to the operator; facilitator early-read via
operator collusion; facilitator key loss before reveal; plaintext in browsers (drafts, queue,
decrypted views) and in downloaded files; derived-field swaps within a sprint; no key rotation on
participant removal within a sprint (future writes after removal still use the current version;
the server simply stops serving the removed person).
